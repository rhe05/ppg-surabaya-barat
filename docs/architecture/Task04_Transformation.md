# Task 4 — Transformation Strategy (Migration 004)

> Status: **APPROVED**
> Scope: everything between immutable `snapshots/` (Task 3 output) and the Validate stage
> (Task 2, Stage 4). Output is the **Canonical Data Model** written into `staging/enriched/`.

## 1. Canonical Data Model

- **Source independence**: the canonical model has no concept of "sheet row" or "Firestore doc."
  A transformer's output must be indistinguishable whether the source was Sheets or Firestore.
- **Naming convention**: `snake_case`, consistency with the *existing* Supabase schema
  (`20260805080137_database_foundation.sql`) takes precedence over inventing new naming.
- **Ownership**: each canonical field has exactly one designated source-of-truth system per
  entity, recorded in `contracts/ownership/<entity>.json` — a property of the *field*, per
  entity per kelompok, not a blanket rule.
- **Extensibility**: canonical schema is versioned (`canonical_schema.json` carries a
  `schemaVersion`).

Output: `contracts/canonical/<entity>.schema.json` — hand-authored, checked into `docs/`.

## 2. Field Mapping Strategy

`contracts/mappings/<entity>.mapping.yaml` per entity, per source system. Mapping principles:

- **Rename rule**: 1:1 source-field → canonical-field, direction always source→canonical.
- **Required fields**: absence is a transformation-time error → `rejected_records.json`.
- **Optional fields**: absence is legal, field omitted (not written as `null`) unless nullable.
- **Deprecated fields**: listed explicitly in an `ignored:` block, never left absent by omission.
- **Default values**: only permitted for fields the business rule engine (§9) declares safe to
  default — defaulting lives in the business-rule layer, not the field-mapping layer.

## 3. UUID Mapping Strategy

**Decision: deterministic (UUIDv5, namespace + legacy-id)**, not random UUIDv4. Rationale: makes
the whole pipeline safely rerunnable — Load's idempotency guarantee (Task 2, Task 6 §5) depends
on the same legacy record always transforming to the same UUID.

```text
state/mapping/
├── uuid-namespace.json              # fixed namespace UUID per entity type — NEVER regenerated
├── santri/
│   ├── legacy-to-uuid.json          # { "<source>:<legacy_id>": "<uuid>" }
│   └── uuid-to-legacy.json          # reverse index
├── guru/ kelompok/ desa/ ppg/ jadwal_kbm/ absensi/ ...
└── _manifest.json                   # which entities' maps are complete vs. partial, per runId
```

- **Lookup performance**: per-entity map loaded once into memory per Transform run.
- **Resume compatibility**: maps are keyed and appended, never rewritten wholesale.
- **Rollback compatibility**: `state/mapping/` is never deleted or regenerated by a rollback.

## 4. Relationship Transformation

**Processing order**: reference tables first → entity tables → transaction tables last
(absensi/jurnal_kbm).

- **Orphan detection**: unresolved child records written to
  `staging/enriched/<entity>/_unresolved.json` with the raw legacy reference preserved.
- **Missing reference handling**: an unresolved FK is a Transform-stage *output*, not a
  Transform-stage *failure* — blocking decision belongs to Validate (Task 5).
- **Circular dependency considerations**: no genuine cycles exist in the current entity set
  (audited). `users.guru_id` ↔ `guru` soft-cycle resolved by treating `guru` as authoritative,
  one-directional only.

## 5. Enum Normalization

`contracts/enums/<enum-name>.enum.yaml` per logical enum: canonical value set + `aliases` map +
optional `default`. An alias-map lookup miss is fatal-for-that-record, routed to
`rejected_records.json` — stricter than FK-orphan handling since an unrepresentable status is a
real data-integrity risk.

## 6. Date & Time Normalization

- Dates: timezone-naive `date`. True timestamps: `timestamptz` normalized to `Asia/Jakarta`
  (WIB, UTC+7).
- Every date format actually observed in Task 3 snapshots explicitly enumerated; anything outside
  that set is rejected, never best-effort-parsed.
- Empty vs. invalid dates are distinguished — empty is legitimate "not recorded" only where the
  contract marks the field nullable.

## 7. Boolean & Numeric Normalization

Explicit truthy/falsy alias table per field (not a universal heuristic). Strict format validation
for integer/decimal parsing. Empty string never passed through as numeric/boolean — always mapped
to `null` (if nullable) or a required-field violation.

## 8. Text Cleaning Strategy

Trim, collapse duplicate whitespace, Unicode NFC normalization, UTF-8 validation (not
conversion), control character removal. Never changes case or semantically meaningful punctuation
in stored values — case-folding is scoped only to lookup-key matching (§4), never the canonical
stored value.

## 9. Business Rule Transformation

`metadata/business-rules-registry.json` — every rule declared, target field, one-line rationale.
Categories: derived fields (recommend **not** materializing date-derived fields), calculated
values (out of scope — belongs in application/reporting layer), status/lifecycle conversion
(highest risk, requires `reports/decisions/` sign-off), default value injection (visible in the
rule registry, separate from field mapping).

## 10. Multi-Source Harmonization

**Ownership-first**: for kelompok 1's `absensi`, Firestore is authoritative per the live
migration — the Sheets copy is stale/historical, not merged field-by-field. For entities without
a clean ownership boundary: last-write-wins by extraction-observed timestamp, or
Sheets-authoritative-pre-cutover / Firestore-authoritative-post-cutover per kelompok. Every
decision logged to `artifacts/reports/harmonization-log.json`.

A general field-level 3-way-merge conflict resolver was considered and **rejected** as
over-engineering given the actual data topology.

## 11. Transformation Pipeline

10 ordered sub-stages per entity: Text Cleaning → Field Mapping → Enum/Date/Numeric
Normalization → UUID Assignment → Relationship Resolution → Multi-Source Harmonization →
Business Rules → Contract Check → output to `staging/enriched/<runId>/<entity>.json`.

Checkpoint granularity: one checkpoint per `(entity, sub-stage)` pair in
`state/checkpoints/<runId>/<entity>.<substage>.json`.

## 12. Error Handling

| Class | Handling |
|---|---|
| Recoverable/transient | retried with backoff |
| Fatal (run-level) | aborts entire Transform stage immediately |
| Partial failure (record-level) | routed to `rejected_records.json`, does not block the rest |
| Malformed records | rejected at earliest detecting sub-stage, raw record embedded |
| Skipped records | logged distinctly as `skipped`, never conflated with `rejected` |

## 13. Output Artifacts

`contracts/canonical/`, `contracts/mappings/`, `contracts/enums/`, `contracts/ownership/`,
`state/mapping/`, `staging/enriched/<runId>/`, `artifacts/reports/statistics.json`,
`artifacts/reports/harmonization-log.json`, `artifacts/reports/transform-report.json`,
`artifacts/rejected/rejected_records.<entity>.json`,
`artifacts/unresolved/<entity>._unresolved.json`, `logs/<runId>/transform.<entity>.log`.

## 14. Quality Considerations

Batch-bound processing for absensi only; every other entity loads fully into memory.
Deterministic execution — no wall-clock timestamps, random IDs, or non-deterministic ordering
embedded in canonical data itself. Source independence (§1) + declarative mapping files (§2) mean
a future source system needs only a new mapping file, no changes to §3–§9.
